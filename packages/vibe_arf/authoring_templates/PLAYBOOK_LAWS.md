# VIBE ARF Playbook Laws



Canonical executable-law mirror. Generated playbooks inherit the applicable laws; wording is sourced from `source/modules/40_policies.ordo.module.yaml`.



1. **E1_STRUCTURED_PERSISTENCE** — All durable playbook implementation state must be stored on disk in a structured, inspectable form. The chat is not the source-of-truth for implementation state.

2. **E2_SCRIPT_ONLY_MUTATION** — Managed playbook implementation files must never be edited manually in place. Changes must be applied through deterministic Python mutation tooling with explicit change specifications and durable change records.

3. **E3_MANDATORY_REGRESSION** — Every behavior, invariant, contract, migration, bug fix, or structural rule that can regress must have regression coverage. Every managed change must run the applicable lifecycle verification profile: dependency-aware FAST checks for PATCH/CHECKPOINT work and FULL verification only at explicit CANDIDATE/RELEASE boundaries. No change may become canonical when its applicable required verification fails.

4. **E4_MODEL_ONLY_WHERE_DETERMINISM_ENDS** — If a responsibility can be resolved or validated deterministically from explicit state, artifacts, schemas, rules, or tool output, the playbook must use a deterministic mechanism rather than unsupported model self-judgment.

5. **E5_GENERATED_PLAYBOOKS_INHERIT_VERIFICATION_ARCHITECTURE** — Every generated runnable playbook must inherit the governing laws, a revision-explicit verification profile, an execution responsibility map, an invariant register, and package-local deterministic validators required by its domain.

6. **E6_SINGLE_RESPONSIBILITY_EXECUTION** — Each executable node or gate must own one cohesive responsibility. A deterministic execution node produces evidence; a separate mechanical gate owns blocking PASS/FAIL routing when such a decision is required. Materialization, validation, and handoff must not be collapsed into one executable element.

7. **P1_FIRST_LAW** — A robot may not injure a human being or, through inaction, allow a human being to come to harm.

8. **P2_SECOND_LAW** — A robot must obey orders given by human beings except where such orders would conflict with the First Law.

9. **P3_THIRD_LAW** — A robot must protect its own existence as long as such protection does not conflict with the First or Second Law.

10. **P4_STRICT_EXECUTION_LAW** — Strictly follow all provided instructions, subject to the applicable instruction hierarchy and the preceding laws.

11. **E7_DRY_CHECK_AUTHORITY_SEPARATION** — Dry-check may exercise workflow logic and synthetic fixtures, but must never fabricate or promote human approvals, live external URLs, or other authority-owned evidence into live readiness.

12. **E8_DECLARED_OUTPUT_EXECUTION_CLOSURE** — Every declared output must have an executable production path or an explicit lifecycle-deferred status with machine-readable rationale; a declared-but-unproducible output blocks readiness.

13. **E9_ORDO_LANGUAGE_AUTHORITY** — Canonical Ordo language is the sole semantic source of truth. Runtime adapters, including Ordo Tree Editor, may add target-specific compatibility checks but must never redefine Ordo validity. If canonical Ordo allows a construct and an adapter rejects or misexecutes it, repair the adapter rather than narrowing the generated playbook.

14. **E10_ANALYST_VISIBILITY_BARRIER** — — A machine-detectable generated-playbook defect is internal repair work. Vibe must not hand a candidate to the analyst for manual YAML/Editor debugging while any required trusted regression or generated-playbook contract gate is failing.

15. **E11_TEST_SCENARIO_SEPARATION** — Auto Answers, replay fixtures, UI sequencing, and adapter test-harness limitations belong to the test-scenario or adapter layer. Do not mutate business semantics or playbook state solely to satisfy a test harness.

16. **E12_INFORMATION_FIRST_AUTHORING** — Before synthesizing an executable process graph, Vibe must model required artifacts, information objects, semantic groups, typed information dependencies, validation/authority boundaries and information lifecycle, and must deterministically validate that authoring information model.

17. **E13_INFORMATION_PROJECTION_TRACEABILITY** — The executable Ordo graph is a projection of the validated authoring information model. Once synthesis begins, every required authoring entity must map to ordinary Ordo and every authoring-managed Ordo element must trace back to the authoring model; authoring-only constructs must not extend Ordo syntax.

18. **E14_SELF_HOSTED_INFORMATION_MODEL** — Vibe is itself a standard Ordo playbook and must satisfy the same information-first authoring, persisted AIM, deterministic AIM validation, and bidirectional AIM-to-Ordo traceability contract that it requires from generated playbooks. No special graph-first or unverified authoring path is allowed for Vibe itself.

19. **E15_PROPOSAL_AUTHORITY_CANONICALIZATION** — Model-generated proposals are hypotheses, not canonical truth. Vibe must keep proposal state separate from approved projection/canonical state, persist field-level human authority in a revisioned ledger, and prevent rejected or unconfirmed proposal values from materializing into artifacts.

20. **E16_SIMULATION_BEFORE_ANALYST_VISIBILITY** — For runnable generated playbooks, Vibe must qualify the exact candidate through the pinned runtime simulation contour before analyst-ready handoff when the simulation dependency is applicable. Fixture or runtime-adapter defects are repaired in their owning layer; canonical-valid playbooks must not receive adapter workarounds.

21. **E17_BEHAVIORAL_COVERAGE_TRUTH** — Behavioral coverage must be derived from an explicit required scenario matrix and execution evidence. Aggregate PASS, VERIFIED, complete, approved, or materialized claims are invalid when their producing gate/evidence has not yet executed or when required scenario families remain uncovered.

22. **E18_EXECUTABLE_DETERMINISTIC_CONTRACT** — Every deterministic generated-playbook responsibility must have a structured executable contract sufficient for deterministic execution and validation without natural-language guessing or LLM recovery. Package-tool and materialization nodes must declare their executor/tool/effects, and artifact/archive validation must be backed by an explicit materialization registry with validator and membership/hash evidence contracts.

23. **E19_STRICT_ROUTE_CLOSURE** — Every static `next`, `on_pass`, `on_fail`, recovery, or equivalent transition target must resolve to a declared executable element, a declared external terminal, or a canonical Ordo reserved terminal construct. Adapter convenience words such as `block` are not implicit terminals; canonical `STOP` remains the reserved fail-stop construct defined by Ordo.

24. **E20_SELF_DATA_FLOW_PUBLICATION** — Vibe must publish its own persisted authoring information model through the same discoverable Source Data Flow publication contract used for generated playbooks. The publication under `design/` is a deterministic, hash-bound projection of canonical `authoring/` data and must never become a second editable source of truth or redefine Ordo semantics.

25. **E20_REFERENCE_ARTIFACT_FIDELITY** — When an explicit reference artifact or exemplar is supplied, Vibe must compile a provenance-aware coverage contract that separates observed structure/content expectations from example-specific facts, and later verify that the materialized artifact preserves every required covered contour or configured fidelity threshold.

26. **E21_DERIVE_PROPOSE_CONFIRM_INTERACTION** — Information already derivable from accepted sources or state must be proposed or prefilled before analyst input. Open free-answer interaction is reserved for genuinely non-derivable consequential human-owned decisions; confirmation/edit of a prefilled proposal is not equivalent to re-entering derivable data.

27. **E22_MATERIALIZED_ARTIFACT_SURFACE_CLOSURE** — Artifact readiness is proved by the materialized artifact content contract, not by approval/status metadata. Every required artifact field/content contour must be bound to a producer and renderer/assembler path and be present or explicitly inapplicable in the final artifact.

28. **E23_EXPLICIT_HUMAN_GATE_EXECUTION** — A runnable package that contains a human/human_decision gate must provide a legal explicit external decision action that records immutable evidence. Runtime/model adapters must never infer, auto-decide, or silently mechanically reclassify human authority.

29. **E24_OPTIONAL_ARCHIVE_NONBLOCKING** — Optional archive or packaging convenience outputs may block core readiness only when their membership/hash contract is deterministic and verifiable at that lifecycle phase; otherwise they remain explicit non-blocking/deferred delivery contours.

30. **E25_AUTONOMOUS_APPLIED_PLAYBOOK_IMPROVEMENT** — After the first runnable generated playbook candidate is qualified, Vibe must run an autonomous evidence-driven improvement phase when quality evaluation is applicable, optimizing the generated applied playbook rather than waiting for analyst-proposed repairs.

31. **E26_IMPROVEMENT_SCOPE_FREEZE** — During autonomous applied-playbook improvement, the Vibe revision is read-only and only the generated applied playbook may be changed. Vibe must never mutate itself merely to pass its own optimization test.

32. **E27_FROZEN_FIXTURE_ANTI_CHEAT** — Simulated analyst/model responses, scenario membership, fixture version, and candidate hash must be frozen before each revision run. After output or score is observed, those fixtures must not be altered to improve that run; any fixture change creates a new immutable test-set version.

33. **E28_HOLDOUT_EVALUATOR_SEPARATION** — Response simulation, optimization, and evaluation are separate responsibilities. Holdout/adversarial expected outcomes must remain unavailable to the optimizer before evaluation; optimizer feedback is limited to scores and non-leaking deficit evidence sufficient for repair.

34. **E29_BEST_SO_FAR_RETENTION** — Autonomous improvement must preserve baseline and meaningful revisions with scores, hashes, and rationale, and must maintain a monotonic best-so-far pointer so a worse later revision cannot destroy or replace the best accepted candidate.

35. **E30_BUDGETED_NO_ANALYST_IMPROVEMENT** — The autonomous improvement phase must not ask the analyst questions. Unknown business-owned values become explicit unresolved limitations while optimization continues. Quality improvement has no acceptance-score threshold; termination is governed by the three-run best-score stagnation rule, returning the best-so-far candidate and residual deficits.

36. **E31_NORMALIZED_PLAYBOOK_QUALITY_SCORE** — Generated applied-playbook quality uses deterministic signed process scoring and reference-based result scoring. Scoring V3 exposes a numeric `development_score` for every valid exact-candidate evaluated run and a separate nullable `acceptance_score` only for provenance-eligible live acceptance evidence. After hard-eligibility and protected-dimension non-regression gates pass, the optimizer ranks and applies three-run stagnation by `development_score` among eligible candidates only; numeric score must never override a protected-dimension regression or hard guard failure, and it must never substitute subjective quality judgment when the deterministic scorer is available. `acceptance_score` may never be fabricated, zero-filled, or inferred from offline conformance. The score formula remains `(process_score + 2*result_component)/3`; executable process scoring applies a lower floor at `0` (`max(0, raw_process_score)`) with no upper clamp, while result components remain clamped 0..1000.

37. **E32_THREE_RUN_BEST_SCORE_STAGNATION** — Autonomous improvement must not stop on an arbitrary quality threshold. It stops when three consecutive valid evaluated revisions, counted under the configured streak semantics, fail to produce a score strictly above the current best; the exact best-so-far revision is returned even when later revisions are worse or tied.

38. **E33_RESULT_SCORE_REQUIRES_PROVEN_MODEL_RESPONSES** — Formal acceptance result scoring requires provenance appropriate to LIVE_ACCEPTANCE: every model-produced response actually executed by the evaluated path must originate from a real live model call or exact-input replay of a previously captured live call. PSEUDO_LIVE_OPTIMIZATION may instead use blind PSEUDO_LIVE_SYNTHETIC responses bound to exact effective-input hashes for internal pseudo scoring only; such responses are never formal acceptance evidence. A deterministic path that executes no model nodes does not require an artificial model call. development_score and pseudo_playbook_score may exist only under the pseudo-live provenance contract and must never be copied into formal acceptance score fields.

39. **E34_NO_SURROGATE_RESULT_ARTIFACT** — The evaluator may score only the primary artifact materialized by the exact candidate graph during that run. This requirement applies to both pseudo-live and live acceptance modes. A control document, expected output, manually completed artifact, helper-generated replacement, or artifact assembled from hidden reference data is never a substitute for the runtime-produced artifact.

40. **E35_EXACT_INPUT_REPLAY_EQUIVALENCE** — A replayed live model response is formal-acceptance-eligible only when its source is a prior live model call and the complete effective input/context hash matches exactly. Pseudo-live synthetic responses do not claim live replay equivalence, but each synthetic response must be bound to the exact effective input/context hash and must be regenerated when that hash changes.

41. **E36_RESPONSE_PROVENANCE_FAIL_CLOSED** — Response provenance is fail-closed within the active scoring namespace. In LIVE_ACCEPTANCE, missing or failed live/exact-replay provenance makes formal_result_score and formal_playbook_score unavailable/null and forbids acceptance claims. In PSEUDO_LIVE_OPTIMIZATION, lack of live provenance does not stop the offline loop: valid blind synthetic provenance plus exact candidate artifact lineage may produce pseudo_result_score and pseudo_playbook_score, visibly non-acceptance. Pseudo scores must never populate formal score fields.

42. **E37_DECLARED_ARTIFACT_LINEAGE_REQUIRED** — A result artifact is eligible in either pseudo-live or live-acceptance scoring only when run evidence proves lineage from declared compose/materialization nodes to the physical output artifact with exact hash. Post-generation mutation outside the declared graph invalidates result eligibility.

43. **E38_STATIC_FIRST_ARTIFACT_TEMPLATE** — For structured artifacts whose section/layout structure is known at authoring time, the declared template must encode that static structure directly. Model-generated content is limited to genuinely variable semantic bindings; a single free-form body binding such as `document_markdown` must not be used as the primary structured-artifact template body.

44. **E39_TEMPLATE_VALIDATOR_STRUCTURAL_ALIGNMENT** — A validator must not require structural sections or headings absent from the declared artifact template unless an explicit deterministic transformation owns their creation. Template/validator mismatch is a blocking authoring defect.

45. **E40_UNRESOLVED_BINDINGS_FAIL_CLOSED** — Deterministic materialization of a structured artifact must fail on missing consequential bindings or unresolved placeholders. Materializers must never invent, silently default, or reconstruct missing semantic content to make validation pass.

46. **E41_CONSTRUCTIVE_CORRECTNESS** — Do not rely on stronger model instructions when an invalid playbook state can be made structurally impossible. For every authoring responsibility, Vibe must prefer enforceable constraints in this order: schema constraint → typed structure → static template → deterministic generator → deterministic validator → mechanical gate → model instruction. `model_instruction_only` is forbidden when any earlier mechanism can enforce the invariant. Any model-only exception must persist explicit evidence explaining why constructive enforcement is unavailable, and generated runnable playbooks inherit the same rule.

47. **E42_DATA_LAYER_CANONICAL_SOURCE** — The persisted data/information layer is the sole semantic authoring source of truth. Process decomposition, runtime graph and Ordo source are derived projections, never parallel authoring surfaces. Every semantic change must mutate and validate the data layer first; upstream changes invalidate downstream projections, and direct semantic edits to generated graph/source are forbidden. Exact projection lineage/freshness must be mechanically verified before downstream verification or release.

48. **E43_REUSABLE_AUTHORING_TEMPLATES** — Generated playbooks MUST instantiate the package-local reusable authoring template kit for information model, bindings, document structure, materialization, deterministic validation, and editor projection before domain specialization. Known contract shapes MUST NOT be recreated ad hoc from model memory.

49. **E44_HYBRID_REFERENCE_FIDELITY_FEEDBACK** — Result-quality evaluation must combine deterministic mechanical penalties and evidence-grounded analytical penalties. Every penalty must emit traceable evidence, what is missing or weak, and concrete remediation. A bare numeric score is insufficient; consolidated defects are mandatory optimizer input, and 1000 is impossible while any mechanical or analytical defect remains.

50. **E45_DETERMINISTIC_FIRST_EXECUTION** — Every executable responsibility must be classified before node synthesis. If an operation is algorithmic or can be computed from explicit state, schemas, dependency graphs, bindings, or tool output, it must execute through Ordo-native deterministic semantics or a concrete package-local deterministic tool; model judgment is forbidden for that operation. A model node is permitted only when persisted evidence explains the genuinely nondeterministic semantic decision that remains after deterministic preprocessing. Generated runnable playbooks inherit the same classification, implementation, and validation rule.

51. **E46_INFORMATION_PRESERVATION_MONOTONIC_EVIDENCE** — Authoritative facts must survive model-to-model transformations with field-level provenance and monotonic evidence semantics. A known authoritative field may not silently become unknown, disappear, or be overwritten by a regenerated whole object. Model-owned steps emit patches only; persisted evidence is updated by deterministic merge/append. Conflicting new evidence must be represented explicitly as conflict/resolution evidence. Generated runnable playbooks inherit the same preservation contract.

52. **E47_DYNAMIC_REFERENCE_EVALUATION** — For reference-backed artifacts, analytical evaluation must build a candidate-specific evaluation plan from artifact type, purpose, frozen quality policy, and eligible reference set; a single generic static comparison prompt is insufficient.

53. **E48_MULTI_REFERENCE_REASONING** — Multiple golden standards must be profiled and weighted by recorded relevance. Reference disagreements are explicit `REFERENCE_CONFLICT` evidence and must not be silently averaged into candidate penalties without a precedence rule.

54. **E49_FRESH_DEFECT_DISCOVERY** — Every scored revision must receive a fresh independent comparative pass that searches for new material/major gaps without being bounded by the prior defect backlog. Closing all known defects is insufficient for a perfect score.

55. **E50_GOLDEN_REFERENCE_EVALUATOR_ONLY** — Full golden/reference artifacts are evaluator-only where anti-cheat isolation applies. Selected full reference contents must be materialized through a mechanically validated evaluator-only input bundle before comparative scoring; generator and optimizer are denied bundle access and receive only sanitized defect/remediation targets that describe the missing quality class without exposing golden text or hidden expected output.

56. **E51_EDITOR_VISIBLE_ARCHITECTURE** — Required authoring architecture must be reconstructible in the Editor, not merely present somewhere in the package. The Editor surface must expose semantic groups, variables/information objects, producer-to-consumer dataflow, Ordo bindings, artifact materialization, and archive/package path from a deterministic projection of canonical Data Layer state.

57. **E52_FAST_FULL_DEPENDENCY_AWARE_VALIDATION** — During authoring and iterative tree changes, Vibe must run only dependency-aware impacted FAST checks from a trusted checkpoint. Full heavy verification is reserved only for explicitly requested CANDIDATE/RELEASE boundaries and must never be inferred or escalated from PATCH/CHECKPOINT because of changed paths or accumulated working changes. FAST selection must be machine-readable, explain why each check was selected, reuse unchanged trusted dependencies, and must not expand to unrelated historical/full regressions merely because a generic source path changed.

58. **E53_DEFAULT_DEBUG_HANDOFF_PROGRESS** — Every authoring session starts in default debug/handoff mode unless explicitly overridden for chat verbosity. From bootstrap onward, Vibe must accumulate a replayable handoff evidence bundle containing intermediate revisions, node/gate outcomes, problems, repairs, tests, checkpoints, and artifact lineage. During autonomous execution it must publish concise progress events at meaningful stage/node/gate transitions so the user can see what is happening and where execution is going next. A quiet-chat override may reduce progress messages but must not disable evidence capture. Generated runnable playbooks inherit this default when their execution context supports progressive chat output.

59. **E54_GENERATED_PLAYBOOK_PRODUCTION_PACKAGE_CONTRACT** — The generated playbook package is a first-class controlled artifact. The default production package must be an allowlisted, self-contained surface sufficient to run, edit, validate and rematerialize the playbook, including canonical Ordo source, canonical Data Layer/authoring model, reusable templates/bindings, Editor projection/support, deterministic runtime/materialization tools and production verification contracts. Development history, intermediate reports, verbose traces, screenshots, simulation/evaluator evidence, undeclared golden/reference artifacts and interpreter caches are excluded from production by default and belong to a separate debug/handoff contour. A stable analyst-provided reference may be retained only when explicitly classified under the production `analyst_context/` surface with evaluator-only access metadata and anti-cheat isolation. Every included artifact class must have a declared purpose and inclusion rule. Files under `generated_outputs/` are excluded by default and may enter production only through an explicit production-deliverables manifest with an allowed delivery role and exact content hash; simulation, evaluator, calibration, reference-like, expected-output, and best-candidate artifacts are never production deliverables merely because they exist under that path. Package validation must fail closed on missing required surfaces, forbidden files, unclassified artifacts, or undeclared/unsafe generated outputs.

60. **E55_ANALYST_CONTEXT_PRODUCTION_PRESERVATION** — Analyst-provided information that may be needed for future editing, evaluation, rematerialization, or source refresh is production authoring context, not debug baggage. Every such source must be classified by authority, volatility, future use, retention mode and access scope. Stable authoritative content may be embedded; stable golden/examples may be embedded only as evaluator-only context; large or volatile sources default to provenance + summary + refresh-required record so stale snapshots do not become false source of truth. Future edits must inspect this context and refresh stale sources before relying on them.

61. **E56_OPTIMIZATION_REGIME_BEST_VALID_STAGNATION** — Autonomous optimization must freeze one evaluation regime per comparable run, score only valid exact-candidate revisions, keep fresh discovery separate from known-defect regression, optimize relevance-weighted consensus rather than golden identity, and return the highest-scoring valid best-so-far revision. Strict improvement resets stagnation to zero; only valid non-improving evaluated revisions increment it; invalid/ineligible revisions receive no score and no stagnation increment. Score 1000 is not a target. Remediation must distinguish PLAYBOOK_CAPABILITY from SOURCE_EVIDENCE_REQUIRED, and unsupported golden-specific facts must never be fabricated.

62. **E57_PRODUCTION_DEPENDENCY_CLOSURE** — Production packaging must be derived from an explicit dependency/reachability closure rather than broad directory inclusion. Executable tools referenced by the responsibility map, verification scripts referenced by the verification profile, embedded runtime/editor roots, declared exact dependencies, and their package-local imports/references form the allowed production support surface. Unreachable mutation/repair/history tooling, unreferenced tests, and undeclared support files are excluded by default. The closure is hash-bound, validated before packaging, and any change to a reachable dependency invalidates the closure until it is rematerialized.

63. **E58_REUSABLE_DATA_EXECUTION_PATTERN_LIBRARY** — Reusable pattern reuse is Data-Layer-first. Pattern applicability is resolved while the canonical Data Layer is being authored from requirements frozen before library lookup; each selected pattern instantiates/binds its own mini Data-Layer module with pattern id/version/bindings/digest provenance. The complete project Data Layer must reach canonical + information-model PASS before any pattern execution projection is derived. The execution/tree facet is then a deterministic projection of the validated instance and must not independently re-select, reinterpret, or silently replace that pattern. Final generated source must materially realize every selected fragment as the exact derived component IDs/types/internal edges; blueprint-only selection is not graph realization. Exact fits are automatic reuse defaults; partial fits require recorded semantic fit reasoning; ad-hoc synthesis is allowed only when no compatible canonical pattern exists or an explicit incompatibility is recorded. The canonical pattern library is a required production authoring surface so fresh chat/editor sessions retain the same Data-Layer-first reuse capability.

64. **E59_PATTERN_REUSE_OPTIMIZATION_INCENTIVE** — Reusable-pattern optimization rewards are positive, mechanically verified process incentives. Each distinct preexisting semantic responsibility frozen before library lookup earns +50 process points only when it is satisfied by a valid canonical Data-Layer pattern instance, a post-canonical derived execution projection, and exact final graph-realization PASS. Duplicate, forced, redundant, pattern-created, blueprint-only, or otherwise unverified responsibilities earn no reward. A mechanically proven missed fit or selected-but-unrealized pattern is surfaced as a +50 potential optimizer opportunity with zero immediate score effect, not a hidden penalty. Analyst-facing open/free-answer parameter requests cost -30 for the first requested variable in each interaction plus -10 for every additional requested variable in that same interaction, regardless of semantic-group membership. This prevents score gaming by collapsing many analyst inputs into one large open question and rewards deriving justified dependent parameters from fewer analyst-supplied variables.

65. **E60_QUALITY_INCENTIVE_ANTI_GAMING** — Quality optimization must not trade analyst effort for fabrication, under-modeling, duplicate penalties, or reward farming. A human/analyst-authority or approval value used without valid authority evidence makes the revision ineligible for scoring; other mechanically evidenced unsupported inferences cost -100 each up to -300. Useful internal or derived variables are free, while each mechanically proven redundant variable costs -10 up to -100. For one interaction, a mechanically proven group-collapse penalty suppresses the weaker cross-group scope penalty for that same interaction, while base interaction/additional-variable burden and independently evidenced harms may still stack; the same defect evidence must never be charged twice within one family. Each mechanically qualified reusable-pattern event remains +50, but its aggregate contribution to process score is capped at +200 and excess raw reward remains visible only for diagnostics.

66. **E61_OPTIMIZATION_RUNTIME_EFFICIENCY** — Optimization runtime performance is an independent evidence track from quality/score. VIBE must profile every valid evaluated revision by scenario and major phase, preserve the active score regime and consequential-gap semantics, diagnose orchestration waste before architecture cost, and never treat lower wall-clock as quality improvement by itself.

67. **E62_ONE_PASS_CALLBACK_SEMANTIC_CACHE** — Pseudo-live execution should use one-pass in-process model callbacks over exact runtime-effective input when supported, rather than restart-from-zero fixture discovery. Immutable compile/inspect work may be reused only under a semantic cache key bound to exact candidate content, runtime/compiler-kit versions and compile-affecting configuration; changed effective model input invalidates response reuse.

68. **E63_TIME_DEGRADATION_CONTROL** — VIBE must record machine-readable timing evidence for every valid evaluated revision and run a configurable OPPORTUNITY diagnostic for unexpected time degradation. The default diagnostic multiplier may be 1.35 over the recent valid same-regime median, but it is configuration rather than a hard quality threshold and has zero score effect until separately calibrated.

69. **E64_PERFORMANCE_AB_AND_CONVERGENCE** — Performance changes require controlled same-regime A/B evidence and must preserve artifact semantics, active gaps, evaluator/scoring regime and externally relevant trace semantics. Independent benchmark scenarios should run in parallel when isolation is proven. Latest revision is not the continuation point by default: retain best-so-far, exclude invalid attempts from stagnation, and stop quality optimization after three valid non-improving revisions before formal Live Acceptance.

70. **E65_THREE_PROFILE_DISTRIBUTION** — Every releasable playbook version must be deterministically materialized from one exact canonical source identity into EDIT, CLI_RUN and MODEL_RUN sibling profiles. Release requires all three; candidate work may materialize the analyst-requested subset. Each profile has an independent dependency closure and profile-specific startup contract, while version, canonical source identity and business semantics remain identical. Execution profiles fail closed on forbidden authoring, evaluator or runtime-authority leakage.

71. **E66_INCREMENTAL_ANALYST_FACT_STREAM** — Interactive analyst conversation is a continuous evidence/fact stream, not positional form submission. Generated playbooks must accept full, partial, incremental, reordered and wider-than-question input; extract all relevant supported facts from each message; deterministically merge them into canonical state; then recompute normalization, evidence audit, conflicts, gaps and completeness before planning the next question. Relevant extra facts must not be discarded or re-asked merely because they were supplied outside the active question.

72. **E67_STRUCTURAL_FIELD_RESOLUTION_STATUS** — Substantive field resolution is structural and canonically represented independently from the field value. At minimum generated interactive playbooks must distinguish KNOWN, UNASKED, UNKNOWN_CONFIRMED and INAPPLICABLE. Empty/null or the textual token UNKNOWN never implies a resolution state by itself. UNKNOWN_CONFIRMED requires explicit analyst/evidence provenance; INAPPLICABLE requires a reason; UNASKED remains unresolved for interactive completion.

73. **E68_INTERACTIVE_COMPLETENESS_AND_CANONICAL_SYNC** — Zero active blocking gaps is not sufficient for materialization. Before compose, every substantive field must be KNOWN, UNKNOWN_CONFIRMED or INAPPLICABLE; any substantive UNASKED field is a hard interactive-completeness block. Accepted facts, explicit corrections and confirmed unknowns must update one canonical truth and all dependent projections before the next question; ambiguous contradictions become conflicts rather than silent overwrites, and confirmed unknowns are not re-asked without new conflicting evidence.

74. **E69_ANALYST_INTERACTION_ROBUSTNESS** — Generated interactive playbooks must treat Analyst Interaction Robustness as a verification dimension covering chunking invariance, input-order invariance, off-shape assimilation, correction handling, explicit-unknown semantics, no redundant re-asking, completeness before compose and analyst-visible progress. Long operations emit ENTER before work and RESULT/NEXT after work without exposing chain-of-thought. This dimension is diagnostic with zero score effect until separately calibrated.

75. **E70_ADAPTIVE_COMPLETENESS_PROFILE** — Generated playbooks must classify case-relevant information dimensions with an adaptive completeness profile that distinguishes REQUIRED_CONSEQUENTIAL, DERIVABLE, OPTIONAL, IMPLEMENTATION_DETAIL and INAPPLICABLE. Completeness applies to consequential scope, not every template field: required consequential dimensions must reach a legitimate structural resolution, derivable dimensions must be derived before analyst escalation, and optional/downstream details must not create artificial analyst burden or synthetic UNKNOWN values.

76. **E71_DERIVED_OUTPUTS_FROM_CANONICAL_CONTRACT** — Outputs that follow mechanically or logically from accepted canonical rules—such as positive/negative/error/missing scenarios, test cases, edge matrices, calculation examples, mappings and traceability summaries—must be derived by the playbook with explicit derived provenance instead of being requested from the analyst. Test adequacy is measured by meaningful canonical-rule coverage and concrete expected outcomes, not fixed row counts.

77. **E72_HYBRID_ARTIFACT_QUALITY_VALIDATION** — Artifact readiness requires hybrid validation: deterministic guards own mechanically decidable invariants while a structured semantic model quality gate evaluates flexible completeness, coverage, consistency and practical usability against canonical scope and a case-adaptive rubric. The semantic validator is read-only over canonical state, may not override deterministic failures, may not invent requirements outside accepted scope, and must not receive hidden golden answers, expected scores or competing-candidate rankings.

78. **E73_QUALITY_SELF_REPAIR_AND_ALIGNMENT** — Template, completeness profile, derived-output strategy and validators must be aligned so every substantive artifact section has an explicit resolution strategy and mixed-authority content retains field/assertion-level provenance. Structured quality findings must be deterministically classified as DERIVABLE_FIX, SOURCE_REQUIRED, ANALYST_DECISION_REQUIRED or IMPLEMENTATION_DETAIL; derivable fixes are repaired before analyst escalation, and materialized UNKNOWN is permitted only for a structurally confirmed unknown with provenance.

79. **E74_EXACT_DISTRIBUTION_PACKAGE_VALIDATION** — Before any EDIT, CLI_RUN or MODEL_RUN distribution is handed to a user, VIBE validates the exact final ZIP bytes with one deterministic validator. EDIT enforces the engineering/Editor surface; CLI_RUN enforces strict-runtime closure and clean context; MODEL_RUN enforces model-execution closure without CLI authority or EDIT-only authoring surfaces; release validation proves all three share one exact canonical source identity.

80. **E75_AUTHORING_EXECUTION_WATCHDOG** — Deterministic authoring and verification tools run through a shared execution watchdog with a default hard timeout of 60 seconds. Any longer declared timeout requires an explicit long-running reason; timeout terminates the process tree, records structured timing/diagnostics, forbids blind identical retry, and feeds an AUTHORING_TIME_DEGRADATION OPPORTUNITY diagnostic with zero score effect until calibrated.

81. **E76_MODEL_MODE_SEMANTIC_REFERENCE** — When a generated playbook targets both model-led execution and a strict CLI/runtime, canonical semantics must first reach a terminal successful execution in Model Mode; that exact trace becomes the semantic reference for later runtime equivalence. A runtime divergence is an adapter/runtime defect unless the canonical playbook contract itself is proven wrong.

82. **E77_STATE_DIFF_AND_REENTRY_SEMANTICS** — Generated playbook node output is applied as a state diff: unrelated state survives every partial write and deletion requires an explicit contract. If routing returns to a previously executed node after authority resolution, repair or another loop, the current node executes again; historical visitation or prior answers are not completion evidence.

83. **E78_GATE_RECOVERY_EDGE_IS_EXECUTABLE** — A gate FAIL follows its declared on_fail route as a real recovery edge. Validation failure is terminal only when the canonical graph defines no recovery route; repair remains local to the causal surface and must preserve unrelated state and previously resolved human authority.

84. **E79_NO_RUNTIME_WORKAROUND_DATA_LAYER_POLLUTION** — VIBE must not compensate for CLI, runner, checkpoint or adapter defects by inventing business/Data-Layer variables such as technical checkpoint or historical-visit flags. Engine defects belong to runtime/adapter repair and regression evidence, while the applied Data Layer remains semantic.

85. **E80_EXHAUSTIVE_AUTHORITY_DISCOVERY_AND_STABLE_DECISIONS** — Before asking an analyst, a generated playbook must exhaustively discover all simultaneously known consequential human-owned decisions in the same information group, assign stable decision_id values, preserve partial answers, and ask again only for unresolved, newly discovered or newly conflicted decisions. UNKNOWN_CONFIRMED counts as a resolved authority decision unless new conflicting evidence appears.

86. **E81_FULL_RECOVERY_LOOP_REGRESSION** — Any generated playbook that declares recovery edges must include end-to-end regression coverage of VALIDATE FAIL → on_fail → local repair → recompute or rematerialize → revalidate PASS. The regression must also prove unrelated state survives and previously resolved analyst decisions are not redundantly re-asked.

87. **E82_DETERMINISTIC_TOOL_STATE_UPDATES_V1** — Generated deterministic, package and materialization tools must return the state_updates_v1 result envelope: report contains diagnostic/evidence output and state_updates contains the only fields eligible for canonical state merge. Executors merge state_updates by diff and must never infer state mutations from report text, stdout, wrappers or undeclared top-level fields.

88. **E83_VISIBLE_DEBUG_TIMING_BASELINE** — Debug timing shown to the user must use actual runtime/server UTC markers and compute elapsed time from the previous marker that was actually visible to the user. Hidden/internal telemetry may be recorded but must never advance or reset the visible timing baseline.

89. **E84_APPEND_ONLY_SELF_REPAIR_LOG** — When a generated playbook repairs a derivable or mechanical defect during execution and continues, it must append a structured self-repair record containing problem, root cause, files or surface changed, repair, validation evidence and continuation point. The hash-chained log is execution/handoff evidence rather than business state or acceptance evidence, and successful continuation must not erase the upstream generator defect signal.

90. **E85_STANDARD_QUALITY_HARDENING_SUBPROCESS** — VIBE provides a first-class cross-domain Quality Hardening subprocess. When explicitly requested or when playbook-quality defect evidence exists, the process captures an exact baseline, classifies defect ownership, defines and proves a RED regression before repair, applies the minimal repair, proves GREEN, runs directly impacted regressions, and confirms a stable quality baseline without weakening acceptance gates.

91. **E86_STANDARD_PERFORMANCE_TOKEN_OPTIMIZATION_SUBPROCESS** — VIBE provides a first-class cross-domain Performance & Token Optimization subprocess that starts only from a stable quality baseline. It measures end-to-end telemetry, ranks hotspots, optimizes one evidence-backed hotspot/hypothesis at a time, proves semantic/quality equivalence before performance acceptance, and rejects any optimization that improves speed or tokens by degrading quality, authority, evidence or readiness semantics.

92. **E87_EVIDENCE_DRIVEN_DEVELOPMENT_SUBPROCESS_ROUTING** — VIBE must recognize explicit analyst requests and observable evidence for debugging/hardening versus speed/token optimization, recommend the matching standard subprocess, and guide the analyst through its declared next step instead of inventing an ad-hoc method. Performance requests with an unstable quality baseline route through Quality Hardening first; diagnostics remain separate from hidden chain-of-thought.

93. **E88_CONTEXT_RUNTIME_EFFICIENCY** — Generated playbooks treat model-visible runtime context as a first-class performance surface. Normal Model Mode execution must avoid recursive package preload and full-source preload, load active-node prompts/knowledge lazily through declared references, keep authoring/editor assets outside normal execution context, distinguish filesystem scans/tool output/model-loaded content/platform overhead, and prefer compact references, material-dependency fingerprints and hash-bound deltas for repeated work. Context optimizations are accepted only with end-to-end measured improvement and semantic/quality equivalence.

94. **E89_PROFILE_AWARE_PACKAGING_CONTINUITY** — Every generated package profile is a deterministic consumer projection of one canonical source, with graph/startup/prompts/knowledge/tools/tests/fixtures projected together from the retained contract. Orphan references, stale canonical-only startup instructions, independently edited profile semantics, or historical-candidate source authority are continuity defects and fail closed.

95. **E90_VALIDATOR_APPLICABILITY_BY_PROFILE_STAGE** — Every validator must be applied only to the package profile and lifecycle stage it declares. Before repairing a FAIL, VIBE classifies it as a real package/playbook defect, a verifier-applicability defect, or an environment/tooling defect; it must not add fake artifacts, reintroduce pruned graph elements, or contaminate runtime packages merely to satisfy a non-applicable check.

96. **E91_REPRODUCIBLE_PROFILE_BUILD_AND_HANDOFF** — EDIT, CLI_RUN and MODEL_RUN package assembly must be reproducible from the same canonical source using sorted members, fixed ZIP timestamps, normalized permissions, exact allowlist/dependency closure, and a machine-readable PACKAGE_CONTINUITY_MANIFEST recording version, source identity, closure/member hashes, startup hashes, validator-policy identity and rebuild recipe. Exact ZIP validation precedes delivery.

97. **E92_DETERMINISTIC_FIRST_ARCHITECTURE** — Every generated playbook enforces deterministic-first execution boundaries: mechanical responsibilities belong to deterministic runtime; model state mutations use hash-bound `state_patch_v1` applied by deterministic code; producer output is validated before persistence/receipt creation; lifecycle closure is monotonic unless an evidence-bound reopen is accepted; repairable recovery derives a deterministic non-null resume node; finite completeness uses stable-ID accounting; deterministic evidence hydration is hash/allowlist-bound; runtime/session/recovery staging context stays separate from canonical semantic state.

98. **E93_OBSERVABILITY_DEBUG** — Generated playbooks provide cross-domain execution observability without exposing hidden reasoning: every material transition has a hash-chained append-only receipt; per-node telemetry tracks execution count, duration, input/output size and token provenance, dependency fingerprint, route and result hash; startup-read and file-access evidence distinguishes filesystem scans, tool-visible output, model-loaded content and platform overhead; repeated-pass and hotspot diagnostics are optimization signals with zero quality-score effect until calibrated; visible timing follows the actual visible-marker baseline; and debug runs produce a standard evidence bundle or explicitly mark unavailable surfaces without fabrication.

99. **E94_DEVELOPMENT_REGRESSION_GOVERNANCE** — Every material VIBE/generated-playbook candidate change is regression-first: define the protected cross-domain invariant before implementation, capture reproducible pre-change non-PASS evidence or an explicit machine-checkable NOT_APPLICABLE reason, apply the minimal change without weakening acceptance semantics, prove the exact regression and directly impacted checks GREEN before candidate handoff, preserve real failures as regression memory, keep REGRESSION_PROOF separate from LIVE_PROOF, and reserve the full accumulated regression/scenario/profile suite for RELEASE unless explicitly requested earlier. Packaging/context-only changes additionally prove declared semantic source identity unchanged, and generated coverage counts remain explainable from the retained contract.
100. **E95_QUALITY_OPTIMIZATION_GOVERNANCE** — Quality and optimization decisions preserve separate correctness, safety/authority, efficiency and artifact-quality dimensions. Hard-law compliance earns no bonus; uncalibrated diagnostics remain OPPORTUNITY with score_effect=0 until independently calibrated. A valid best-so-far candidate is not replaced by latest by default. Performance/token/local metric gains are accepted only with same-regime end-to-end evidence and are rejected if any protected semantic, authority, safety or artifact-quality dimension regresses. Every optimization attempt retains an append-only problem → baseline evidence → hypothesis → protected invariants/regression → change → comparison → measured result → limitation → decision history.

101. **E96_EXECUTION_WRITE_SAFETY_VALIDATOR_GOVERNANCE** — Validator repair and write execution are fail-closed and contract-driven: inspect a validator ID and available implementation/schema before heuristic repair; never issue an investigation/probe write outside the approved change plan; every write declares patch, merge or full_replace semantics; full_replace additionally requires fresh current state, full target materialization, one canonical reviewed scope, drift guard, backup, destructive-effect disclosure, explicit approval and post-state verification; transport success alone is never semantic success; and Data-Layer fields whose interpretation affects writes declare a machine-checkable semantic_value_kind before materialization.
102. **E97_LIFECYCLE_RELEASE_FAMILY_GOVERNANCE** — Authoring master and distribution outputs are separate lifecycle surfaces: runtime profiles are derived projections and must never destructively become the new master; EDIT requires a present, current Data Layer; release requires one canonical EDIT/CLI_RUN/MODEL_RUN family with shared identity; every validation result declares its capability level; validation/build tools declare purity and mutating tools run on qualification copies; release requires structural and behavioral coverage minimums; direct and local execution share planner, write and verification engines except transport; and post-mortem findings are classified as session error, domain discovery, framework defect or platform limitation before reuse.
