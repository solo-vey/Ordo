Execute Playbook API Guide

How an external agent can upload a playbook and Auto Answers, run it through Execute Playbook, and retrieve runtime state and debug evidence automatically.

REST ReferenceOpenAPI YAML
Local integration API. By default, the Editor listens on 127.0.0.1. This API is intended for local automation and agents, and uses the same runtime boundary as the web-based Execute Playbook mode.

What can be automated

An agent can upload a playbook; upload replay/Auto Answers; configure a model provider; create a server-managed run; execute one phase at a time or advance automatically to the next stop; read canonical runtime state and transcript; submit analyst input; stop a run; retrieve artifacts; and fetch a complete debug snapshot immediately after an error.

Recommended workflow

1. Upload the playbook
POST /api/playbook-package
Send the ZIP in data_base64. Save package.id from the response.
2. Upload Auto Answers
POST /api/replay-package
The replay package is registered on the server. Use the returned replay_id as auto_answers_replay_id.
3. Configure the model
POST /api/live-config
Select the provider/model and use the same session_id for the Execute run.
4. Create the run
POST /api/execute-run-start
Send package_id, session_id, and optionally auto_answers_replay_id. You may also set advance:true immediately.
5A. Controlled mode
POST /api/execute-run-step
One HTTP call equals one runtime phase (enter or respond). This is the best mode for an agent that wants to inspect every step.
5B. Automatic mode
POST /api/execute-run-advance
The Editor advances deterministic/model steps and uses Auto Answers until terminal/halt/error or until analyst input is required.
6. Submit manual input when required
POST /api/execute-run-input
Send analyst_input; by default execution continues automatically after the input is accepted.
7. Inspect run status
GET /api/execute-run-status?run_id=...
Returns current_id, canonical state, state_revision, path, transcript, outcome/error, artifact registry, and the debug link.
8. Retrieve all evidence after a failure
GET /api/execute-run-debug?run_id=...
Returns state, history, transcript, the full debug trace, error traceback, artifact registry, and Auto Answers cursors.

Minimal example

# 1) upload playbook
POST /api/playbook-package
{"filename":"PLAYBOOK.zip","data_base64":"..."}
# -> package.id = "abc123..."

# 2) upload Auto Answers
POST /api/replay-package
{"filename":"AUTO_ANSWERS.zip","data_base64":"..."}
# -> replay_id = "def456..."

# 3) create + auto advance
POST /api/execute-run-start
{
  "package_id":"abc123...",
  "session_id":"agent-session-1",
  "auto_answers_replay_id":"def456...",
  "advance":true,
  "max_steps":120
}
# -> run.run_id

# 4) inspect at any time
GET /api/execute-run-status?run_id=execute-...

# 5) if outcome.status == "error" or "halted"
GET /api/execute-run-debug?run_id=execute-...

What run status contains

FieldMeaning
current_idCurrent node/gate.
stateCurrent canonical runtime state.
state_revisionRuntime-owned revision.
transcriptServer-side Execute Playbook transcript: assistant/analyst/system events.
pathThe execution path actually traversed.
awaiting_analystWhether analyst input is currently required.
outcomecompleted, halted, or error with reason/node details.
artifactsCurrent runtime artifact registry; retrieve files through GET /api/run-artifact.
debug_endpointReady-to-use URL for the complete debug snapshot.

How an agent should handle an error

Recommended loop: if outcome.status is error or halted, do not reconstruct the failure from the UI. Call /api/execute-run-debug immediately, save the snapshot, and inspect error, the latest debug_trace, state, path, and artifacts.

An exception during a runtime phase is fail-closed: the server-managed run keeps the state from before the failed call and records the error type, message, node, phase, and traceback. The agent must not invent or substitute a partial state.

Low-level API

POST /api/live-step remains available for the browser UI and specialized integrations. In that mode the caller supplies source, state, revision, history, and the current element. Autonomous agents should prefer the high-level /api/execute-run-* endpoints because the server owns these structures and prevents external clients from accidentally desynchronizing them.

Stopping a run

POST /api/execute-run-stop moves the run to halted / user_stop. Because Execute REST calls are synchronous, stop is applied between runtime phases; it is not transport-level cancellation of an HTTP/provider call that is already in progress.

Security. The API is local and can execute package-local playbook tooling. Use it only with trusted playbook packages. Do not expose the Editor server publicly without a separate authentication and security layer.
